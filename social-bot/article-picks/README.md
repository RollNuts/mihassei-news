# 未発生新聞の記事をXへ自動紹介する

Xの自動投稿はこの`article-picks`経路だけを使う。旧シュール短文、キャラ日常、`useful`独自稿、漫画は自動送信しない。既存のBuffer FreeチャンネルとGitHub Actionsだけを使い、追加費用は0円を維持する。

## 配信

[`x-original-experiments.yml`](../../.github/workflows/x-original-experiments.yml)は毎日09:05・11:05・13:05・15:05・17:05・19:05・21:05頃（JST）のcronを主チェックとし、各枠20分後と40分後にも同じ論理枠を再確認する。GitHub cronが一部遅延・欠落しても次の2時間枠まで待たない。加えて、09:00〜21:59 JSTに`content/articles.json`がmainへ公開されたpushも補助トリガーにする。07:30・23:30枠の公開pushはBufferを読まず書かず終了する。主cron・20/40分後の再確認・公開pushのどこから起動しても1回最大1本、JST1日最大7本、09:05・11:05・13:05・15:05・17:05・19:05・21:05の**論理7枠につき1本まで**、slug重複防止を同じコードで適用する。GitHub Actionsが遅れて09:05枠の処理が09:36になっても、11:05枠は別枠として判定する。ただし、**同じXチャンネルの直近Buffer実送信時刻（sentAt）から2時間未満なら次枠を見送る**。送信中・2時間以内に送信予定・期限超過の予約がある場合も安全側で見送り、後からまとめて流さない。Bufferの時刻が取得不能な送信/予約は0件扱いせず、確認できるまで見送る。旧自動レーンは再開せず、その履歴は記事枠に数えないが、直近の実送信だけは間隔判定へ含める。同一論理枠のcron・公開push重複も止める。選ばれた記事はBufferの`shareNow`でその枠の実行時に即時送信を依頼し、一般のBufferキュー待ちで数時間後ろへ流さない。`createPost`成功応答から同じAPI呼び出し内で`status`・`createdAt`・`sentAt`・`externalLink`・`sharedNow`・`shareMode`も受け取り、初期送達証拠として台帳へ保存する。記事レーン自身の論理7枠だけを日次上限として数え、停止済み旧投稿や他のX投稿は記事枠を消費しない。既存Buffer投稿は重複確認のため読み取るが、記事紹介そのものはキューの空き時刻に依存しない。

- **新着レーン**: 公開1〜18時間の未紹介記事。続報を優先し、その次に新しい記事を選ぶ。PV蓄積前でも対象にする。新着候補を先に重複・上限・安全性で判定し、成熟記事のPV APIが取得できなくても新着紹介を妨げない。
- **Xでの初見理解ゲート**: 新着・実測PVのどちらも、見出しと既存summaryを読んで状況が自立して伝わる記事だけを紹介する。見出し・要約が欠落/極端に短い、書き出しが「この件」「例の」「これを受け」等の文脈依存、または記事に`x_promotion_skip: true`の編集判断がある場合は候補から除外する。機械的な短文チェックだけで面白さを判定したと見なさず、執筆段階の[`初見読者の理解ゲート`](../../docs/EDITORIAL_LOOP.md#初見読者の理解ゲート)を優先する。Xで長文解説を追加して救済しない。
- **話題の偏り防止**: 続報でない通常記事は、当日すでに自動紹介した記事の先頭タグと重ならない候補が上位3件にあればそちらを優先する。候補がなければ元の順位を使い、投稿本数を減らさない。続報は同じ話題を追うこと自体に意味があるため優先を維持する。
- **実測レーン**: 公開12時間以上・21日以内から、サイトと同じ`/api/engagement`の実測PVで選ぶ。直近7日PV、当日PV、実際の公開日時の順で比較する。
- 同じslugは一度しか自動紹介しない。Bufferのscheduled/sentに加え、draft/error/needs_approval/sendingも読み、正規記事URLが残っていればGit台帳の保存失敗後でも復旧して再送を防ぐ。復旧時はproviderのsentAt/dueAtを優先し、まだ送信途中などで両方が無ければcreatedAtから論理枠を推定する。provider時刻が本当に取得不能な場合だけ、重複防止のみ行って現在の論理枠を消費しない。失敗状態を見つけても自動再送しない。
- 災害・戦争・武力衝突・テロ・大量死傷事故に該当する記事は自動紹介しない。
- 本文は、記事に安全な`x_share_lead`があれば**それを先頭の読者向け入口文として使い、見出し＋summaryの定型紹介は省く**。`x_share_lead`は記事単体で意味が通る自然文で、要約の言い換えではなく、読者の生活へ引き寄せる一言、問い、矛盾を一歩だけ強める観察、目に浮かぶ場面などから**その記事に自然な入口を1つだけ選ぶ**。毎回問いかける、「これ5年後の話として書いたんだけど」「正直に言って」等を反復する、といったフォーマット化はしない。運営者本人が体験したと誤認させる一人称の実話風表現、ハッシュタグ、URL、`要約：`等のラベルは入れない。文字数超過・不正なタグ/URL・短すぎる入口文は自動で不採用にし、従来の通常記事`【未発生新聞】`／続報`【続報｜未発生新聞】`＋見出し＋入る場合は既存summaryの短い1行へフォールバックする。どちらの経路でも固定の`#未発生新聞`、最大2個のX向け発見語、追跡付き記事URLを付ける。追加語は「元ニュースが流行っている語」ではなく、**この記事の中心テーマを探す人が実際に入力する語**を使う。特定銘柄は`x_tickers`のCashtag、残りは編集時に確認した`x_tags`を優先する。生の`trend_observation.term`は自動採用しない。trend記事は`trend_bridge.x_discovery_term`と同じ語を`x_tags`または主題銘柄の`x_tickers`へ明示してから候補にする。非trend記事で明示語がない時だけ、**見出し・summaryに実際にある語**から`#ポイ活`、`#タイパ`、`#推し活`等の既知語を保守的に拾う。サイト内`tags` / `satire_tags`はX発見語の推測元にしない。`#アプリ`、`#SNS`、`#社会`など回遊用カテゴリは流用せず、自然な語がなければ追加しない。`#未発生新聞`は全自動記事紹介で必須とする。毎回の「創作」「架空」「フィクション」定型注記は付けない。
- 自動画像添付は行わず、リンク先OGPの公開画像を使う。記事URLには `utm_source=x&utm_medium=social&utm_campaign=article_auto` を付け、サイト既存の匿名・粗粒度な流入計測でX経由を取りこぼしにくくする。完全な参照URLや個人情報は保存しない。

## 発行本数との関係

サイト側は07:30〜23:30の9枠を維持するが、通常運用は07:30〜19:30のコア7本。21:30・23:30は公開失敗・遅延の回収、またはその日のうちに出す価値が明確な強い企画だけの予備枠で、8〜9本目を本数合わせで作らない。Xは全記事を必ず流すノルマではない。重複、危機ニュース、品質、論理枠の使用済み、当日7本上限により見送る場合がある。Actionsの遅延だけを理由に枠を消費扱いにしないが、**実送信間隔が2時間未満なら次の論理枠を見送る**。見送った枠を後から埋めず、弱い記事や古い記事でX枠を埋めない。

## 改善ループ

X文面は投稿ごとに勝ち型を固定しない。送信時に`state.json`へ実際に使った`copy_mode`（`reader_lead` / `headline_summary`）と既存の本文指紋・slug・論理枠を残し、後から「どの文面で送ったか」を再現できるようにする。既存記録に`copy_mode`が無い場合は推測で埋めない。

日次の監視では、実公開を確認できた記事について実際の投稿文、`copy_mode`、公開時刻、取得できるX公開反応、サイト側の`x_arrivals`・`page_views_per_hour`・`continuation_share`を照合する。未取得の反応を0にせず、1投稿だけの好反応・不調で文面規則を書き換えない。日次は「入口が要約へ戻っていないか」「問いかけ等が反復していないか」「記事内容と入口がずれていないか」を観察し、明確な回帰だけ修復する。

週次では公開後経過時間と流入条件が近い複数投稿を比較し、`reader_lead`とフォールバック、さらに実文上の入口の違いを**後付けの固定カテゴリにせず**読む。比較可能な例が片側3本未満、X反応や流入が欠損、題材・公開時刻の差が大きい場合は「学習不足」としてルールを変えない。十分な例がある時だけ、強かった共通点と弱かった共通点を各最大2点に絞り、反例も確認する。継続ルールを変える場合は週次編集の既存原則どおり1点だけとし、問いかけ率などを機械的なノルマにしない。

改善は追加費用0円の既存データと公開情報だけで行い、X分析のための有料API・外部LLM・新規DBを追加しない。
## API利用枠の保護

投稿と送達監査は同じActions concurrencyと`api-budget.json`を使い、HTTP接続前に1要求を記録する。失敗したHTTP要求も数え、直近24時間30要求・直近30日900要求を上限にする。監査は24時間最大7要求、当日の残り6要求とproviderが返す30日枠の残り210要求は投稿向けに確保する。上限を超える場合は未送信のまま見送り、品質・重複・最低2時間の条件を緩めない。1日最大7本の設定は維持するが、利用枠によって全枠を送れない場合は残る。

この台帳は導入後の当該botの要求数であり、アカウント全体の過去の消費を0と見なさない。APIの`RateLimit` / `RateLimit-Policy` / `Retry-After`から残量・期間・解除日時だけを保存し、provider側の制限を優先する。他の連携が同じ枠を使う場合もあるため、無料枠に必ず収まるという保証には使わない。秘密鍵・生のHTTP応答・partition keyは保存しない。台帳を欠損・破損時に初期化して上限を復活させない。

接続確認済みのorganization/channel IDは24時間だけ再利用する。固定チャンネルとの不一致・将来時刻・期限切れは再確認し、投稿一覧・実送信間隔・未送達・slugの照合は投稿前に引き続き実行する。予算は成功・失敗のどちらでも永続化し、送信成功後の残量保存失敗では投稿の受理IDを失わない。

## 確認

投稿処理は、時間外・使用済み論理枠・日次上限・台帳で確認済みの実送信から2時間未満なら、Bufferへ接続する前に終了する。次の空き枠で送る際は従来どおりprovider上の重複・未送達・実送信間隔を再照合する。枠を埋めるための再送や台帳削除は行わない。

`x-delivery-audit.yml`は各論理枠の約30分後（09:35〜21:35）と23:45 JSTに`article-picks/state.json`の直近7日分を読み、保存済みBuffer IDと正規記事URLを照合する。送信済みの確認記録は元の観測日時を保持して再利用し、未確認IDだけを1回最大3件直接読む。アカウント探索や全投稿一覧の取得を監査ごとに繰り返さない。sending/scheduledは15分、その他の未確認・エラーは6時間以内の同一照会を抑制し、読取予算で後回しにしたIDは次回へ渡す。再利用したsentは過去の送達証拠であり、現在のXページ存在確認ではない。draft/error/needs_approvalはdelivery problemとして残し、sendingはcreatedAt等から15分以内なら正常な送信中として分離、15分を超えて残る場合だけdelivery problemに上げる。Bufferが`error`を返した場合は表示用`error.message`とHTTPSの`supportUrl`だけを最大500文字で証拠に残し、内部用`rawError`は取得・保存しない。定時起動の欠落に備え、21:00〜23:59 JSTの`content/articles.json`公開pushでも同じ読み取り専用監査を補助起動する。昼間の記事公開push自身は監査のprovider読み取りをしない。GitHubが定時監査を取りこぼしても、記事投稿workflowの**同一リポジトリ・mainでの完了**を補助トリガーとして監査を実行する（PR・fork由来は除外）。これは投稿処理の完了後に保存済みIDを照会する読み取り専用の補助経路であり、新規送信・再送・旧投稿削除はしない。結果は既存の`article-picks/delivery.json`へ保存する。429を受けたらその実行の残りの照会を止め、取得できた`Retry-After`の解除時刻を同じファイルへ保存する。投稿・監査ともその時刻まではBufferへ接続せず、制限中を成功にしない。解除時刻が返らなければ復旧時刻は未確認のまま扱う。再送・予約編集・X投稿は行わない。

`state.json`に記事slug、Buffer受理ID、本文指紋、選定根拠、必要なPV期間、`slot_jst`、`submission_mode: shareNow`に加え、Bufferが同じ`createPost`成功応答で返した初期`status`・`createdAt`・`sentAt`・`externalLink`・`sharedNow`・`shareMode`を存在する範囲で保存する。移行前の受理記録は`queued_at_utc`から論理枠を推定する。Bufferの即時送信受付はX実公開の独立確認ではないため、provider上のsentとX実公開を分けて確認し、未確認の公開や反応を0扱いしない。台帳を削除して同じ記事を再送しない。

停止は`article-picks/config.json.enabled: false`だけで行う。旧自動レーンは停止状態を維持し、本人の明示的な再開依頼なしに有効化しない。
