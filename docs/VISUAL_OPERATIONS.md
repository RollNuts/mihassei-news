# 表示と画像の品質を維持する運用

対象は公開新聞の読みやすさと画像の内容。担当・予定枠・着手前の重複防止・公開完了は[OPERATIONS.md](OPERATIONS.md)に従う。このページは画像の目視採用と表示検品の正本とする。

## 画像の採用条件

`scripts/generated_photos.py` はJPEGの寸法・容量・SHA・記事指紋を検証する。これは絵の内容の合格判定ではない。

`scripts/visual_review.py` は `content/visual_reviews.json` の目視確認記録を照合する。`decision: accepted`、現在の `article_sha256` と `image_sha256`、タイムゾーン付きの実際の確認日時、具体的な観察メモが必要。生成されたJPEGが保存されただけでは公開採用しない。記事か画像が変われば過去の確認は失効する。

```bash
python3 scripts/visual_review.py
python3 scripts/build.py
```

一覧の `pending` は未検品、`rejected` は品質保留であり、失敗した生成ジョブとは別。発行・改稿担当は今回変更した記事を確認し、残る未検品は[画像回収担当](OPERATIONS.md#画像動画の担当を重ねない)へ引き継ぐ。通常の回収は`attention`と変更対象に限り、正常な既刊全件の再取得・再検品は週次の横断確認へ任せる。現在の記事・画像SHAに一致するacceptedは、新しい不具合がなければ再承認しない。件数を満たすために雑な合格を付けない。

発行・改稿後は非同期のCPU画像ジョブも確認する。今回分の既存ジョブが実行中なら重複起動せず最大15分の範囲で完了を確認し、未起動の場合だけ既存の無料CPUワークフローを最大1回実行する。未検品JPEGを再生成せず、完了後の最新mainから今回変更した記事の画像を実表示する。合格記録の公開後、対象記事・画像・OGP・RSSを照合する。

時間切れ・表示不能は検品完了とせず、[画像回収担当](OPERATIONS.md#画像動画の担当を重ねない)へ引き継ぐ。生成成功だけで終えず、現在の実画像を採用して本番照合するか、不合格を記録して本文に合う専用SVGを本番照合する。写真の採用待ちで記事発行を止めない。自動タスクの保存結果を確認できなければ設定更新済みと報告しない。

失敗・待機超過では再生成を始める前に、既存のCPU run ID・失敗step・artifactを確認する。確認用JPEGは1日保持なので、回収可能な実物は記事指紋と原manifest・seedを検証して再利用する。未検品JPEGや、正常な専用SVGがある品質保留を自動で再生成し続けない。回収の各回は最大3記事、追加生成はactiveな既存無料CPUワークフローのレビュー用実行を最大1回とする。

**新着の画像採用と本番確認を主務とし、既刊の実写化だけを目的とした試作は通常回収から外す。** 既刊は内容の読み誤りにつながる不一致や表示不具合を優先して修復する。新たに単発の既刊実験を行う場合も、**新着の未生成・未検品・汎用代替・実行中のCPU処理が残る間は試作しない。** 過去の不採用原因に対して何を変え、何が写れば改善と判断するかを説明できる時だけ、1つの仮説を1記事・1画像の実験で確かめる。空き時間・残り枠・別の記事名だけを理由に生成せず、同じモデルと場面指示による不合格を繰り返さない。

**無料CPUの既刊試作はJSTの1日につき異なる記事を最大4件・各記事1回まで**を上限であり、達成目標ではない。各回の最大3記事の内数とし、`Photo backfill: <slug>` の当日履歴で失敗・キャンセル・待機中も消費済みと数える。同じ記事の同日再試行とジョブ再実行は禁止。実験結果を実画像で判定してから、次に試す根拠があるかを見直す。採用済み写真を再検品せず、不合格を「補助写真」などに言い換えて再承認しない。

再試験は明示slug・`retry_held=true`・`publish=false`・`backfill_scene`を使い、今回の指示を持つ記事コピーと新しいJPEGをレビュー用artifactへ保存する。通常の生成が除外する `illustration` 記事もこのプレビューだけで試せる。**本番の記事・既存SVG・旧JPEG・manifestは試作時に変更しない。** モデル読込の前後・生成途中・保存前に最新mainを確認し、記事・採否・画像・生成検証コードの更新や通信不能を検出したら試作を中断して新着処理へ場所を空ける。文書やX配信状態など画像待ちを変えない更新だけなら試作を続け、無関係な更新で毎回中断することを避ける。artifactの `source_article_sha256` は試作元、`article_sha256` は新しい場面指示を持つコピーの指紋として区別する。

文章指定の試作で主役や小道具が繰り返し欠落した題材は、[無料CPU画像ルート](FREE_CPU_IMAGES.md)の参照プレビューを比較できる。参照SVGを実表示し、必要な物が大きく存在し、普通のカメラで撮れる位置関係かを確認する。加湿器が描かれていない箱の図、巨大な星やUIなどをそのまま写真化しようとしない。本文と違う図は先に修復する。最初は適した1記事だけを同じ日次上限内で試し、実写品質の確認前に全既刊や通常新着の既定へ広げない。低い変換強度ではイラスト調が残り得るため、参照画像があることを理由に採用基準を下げない。

合格時だけ、最新mainの本文・見出し・出典が試作元から変わっていないことを照合し、新しい `scene_prompt`・`visual_strategy: cpu-photo`・実JPEGの原生成記録・現在の採用記録を同じPRで反映する。必要なSVGフォールバックも実物と本文を再確認する。旧JPEGの指紋やseedを付け替えない。不合格では現在のイラストを維持し、現本文への保留記録に試作元と試作記事のSHA、候補JPEGのSHA、試した指示、run ID、実際の検品理由を残す。生成失敗は目視不合格と混同せず既存の引き継ぎ手順に従う。新着が途中で到着した場合はその回収を優先し、追加の既刊試作は行わない。

回収担当は変更・生成・公開の直前にも停止状態を確認する。`stop_scope`が`all`・`unknown`、CPU無効、状態取得不能なら読み取りだけで終了し、再開しない。Macだけの停止ではローカル生成を起動せず、activeなCPUの成果物の検品・公開は続けられる。空き12GiB・生成JPEG総量1.5GiBの保護を維持する。停止・再開の正本は[MAC_SCENE_SETUP.md](MAC_SCENE_SETUP.md)。

JPEGの状態だけで表示を判断しない。同じレポートの `publication_counts` と各記事の `publication` で、現在のビルドが選ぶ素材（生成JPEG・専用SVG・承認済み写真・汎用代替）も確認する。`attention` は未検品だけでなく、改稿で失効した専用SVGや汎用代替への差戻りも示す。これはローカルの選択結果であり、本番配信の確認ではない。

`attention`が空でも写真の回収完了とは限らない。`photo_followup`は同じ対象（通常は`--slug`で指定）から、写真向けの`cpu-photo`記事で現在は写真が選ばれないものを、現本文SHA・状態・代替画像・次の操作とともに返す。正常な専用SVGを表示障害にはせず、意図的な`illustration`、採用済み生成写真、選択中の承認済み写真は除く。`missing`は古い・不正なJPEGも含む「現本文に使える検証済み写真なし」であり、未生成と断定しない。`pending`は実JPEGの目視採否、`rejected`は不採用理由と既存候補・条件変更の確認へ進む。既存候補や未完了PRを先に回収し、同条件の再生成を繰り返さない。この一覧は新規生成の命令でも本番配信の証拠でもなく、通常対象外の既刊試作を増やす理由にはしない。

既刊を改稿する担当は、変更後の実採用素材まで照合してから公開する。専用SVGが失効した場合は現物と新本文を見直し、なお場面が合うと確認できた時だけSVGの確認用記事指紋を更新する。場面が変わったなら適合する素材へ直すか、具体的な待ち理由を残す。JPEGの生成記録や過去の承認を付け替えて復旧させない。画像待ちで発行を止めず、汎用代替が出ることを見落としたまま画像改善済みと報告しない。

### 場面を変えない文章整理と写真の再利用

見出し・要約・本文を読みやすく直しても、生成時の`assets/generated/manifest.json`は書き換えない。既に採用された`origin: chatgpt-imagegen`の写真で、`scene_prompt`と写っている場面が変わらない場合だけ、改稿後の全文と同じ実JPEGを再表示して照合し、既存の`content/visual_reviews.json`へ現本文SHAの新しい掲載判断を記録できる。画像のSHAを変えるための再圧縮や、再利用のための生成record・seedの付け替えはしない。

通常のreviewに`reuse.kind: same_scene_text_revision`を明示し、原generation recordの`generation_record_sha256`、変更しない`scene_prompt`の`scene_prompt_sha256`、最初の実acceptedを保持した`original_review`、今回どの文を整理し、写真のどの動作がなお一致するかを示す`reason`を添える。generation recordのハッシュはPythonの`json.dumps(record, ensure_ascii=False, sort_keys=True, separators=(",", ":"))`のUTF-8 SHA-256、scene_promptは元の文字列のUTF-8 SHA-256とする。元recordの整数をJavaScript Numberで丸めない。`original_review`を作り直さず、2回目以降は既存の再利用記録から同じ元acceptedを引き継ぐ。

再利用reviewは現在の記事・画像SHA、実際の確認日時、具体的な観察メモに束縛する。確認日時は今回の本文更新と直前reviewより後にする。CIの履歴保護で、元acceptedの実在、原生成record・画像・scene_promptの不変、現在の本文との対応を照合する。未検品・不採用・holdの写真、場面変更、CPU/Mac写真にこの例外を使わない。有効な明示reviewがなければ、従来どおり写真は失効する。単に以前acceptedだったことや、原稿の一文要約だけを新しい目視確認の代わりにしない。

### 実画像と本文の照合

実ファイルを表示し、対応する本文と次を照合する。**記事内容が合っていても、実写に見えなければ生成写真としては不合格**にする。

**実写優先・採用ゲートは緩めない**：写真を載せること自体を成果にしない。一見して普通の報道写真・現場スナップと区別がつかない自然な質感（人物・材質・輪郭・光・影）が第一条件。白っぽく均一なCG調、溶けた人物、架空の店名・商品文字や不自然な構造が目立てば、記事の一部を表現していても不採用。さらに、写真に写っている主役・行為・小道具が現在の本文の主要場面と明確に一致し、記事を読む前後で誤認を生まないことを確認する。**単に倉庫・台所・店など背景が合うだけの写真、または一部の要素だけが合う写真は不採用。** 見た目が写真に届かない時は実写として公開しない。記事本文は止めず、現在の本文に適合する検証済み専用SVG等の安全な代替画像を維持する。**落とした素材を「補助写真」等の呼び方で再承認しない。** 別のJPEG候補を使うならその原本を改めて実表示し、元の生成SHA・記事SHA・撮影らしさと本文の具体的な一致を記録する。新規生成は無料枠と停止状態を尊重し、同じ題材・モデル・指示で不合格を繰り返したら無理に再試験しない。

採用メモでは「本文の場面との一致」と「普通のカメラ写真に見える根拠（自然光・人の肌・材質・影など）」を分けて確かめる。**場面の意味が伝わるという理由だけで、不自然なCG風JPEGを採用しない。**

- **一見して報道写真・現場スナップとして成立するか。** アニメ、イラスト、3DCG、ゲーム画面、コンセプトアート、蝋人形のような肌、プラスチック質感、映画ポスター風の照明、広告・商品写真の過度な光沢、極端なHDRやネオン演出が先に見える画像は不合格。肌・布・金属・紙・食べ物などの材質、光源、影、被写界深度が普通のカメラ写真として自然であることを優先する。
- **風刺は画風ではなく状況で見せる。** 面白くするために非現実的な発光、巨大化、漫画的表情、派手な色調を足さない。普通の場所・普通の人・普通の光で、起きている出来事だけがおかしい写真を最優先する。人物像と題材の幅は[編集方針](EDITORIAL_LOOP.md#分類と紙面の幅日次週次で見る)に従い、場面指示にも本文に合う年齢層・立場を具体化する。真顔は取り組む真剣さであり、疲労・うつむき・棒立ちを必須にしない。試す・遊ぶ・競う瞬間の自然な動作、服の色や表情も本文に合わせる。撮影位置・距離・光・服色を一律に固定せず、直近と同じ構図が続く時は本文内の別の瞬間や、人物を置かない具体物・現場も比較する。
- 主役の人物・具体物が存在し、対象と個数・関係が合うか。牛とロバなら、区別できる2頭が必要。
- 行為と場所が記事の場面を伝えるか。謝罪メールを紙の証書、番組収録を無関係な会議室に置き換えない。
- 不自然な顔・手・融合した物体・宙に浮く物が、意図した創作と無関係に目立たないか。
- 小さいカードと記事の大きな表示で主題が見えるか。トリミングで対象や表紙文字が欠けないか。
- 代替文・クレジット・SNS画像が実際に選択した素材に合うか。写真、合成の再現画像、創作イラストを取り違えない。

不合格は `assets/generated/manifest.json` の `rejected` に記事指紋・対象JPEGのSHA・具体的な理由を記録する。同じ変更で `content/visual_reviews.json` の旧acceptedをrejectedへ更新するか削除し、後の再取込でも過去の合格が復活しないようにする。既存JPEGの生成記録、seed、記事指紋を付け替えて再承認しない。再生成は既存無料経路のみで、品質保留の再試験は明示slugのレビュー用生成として扱う。新しい画像を実際に見てから採用を判断する。

ChatGPT内蔵画像は、本人が依頼した実写風写真の生成・取り込みに使う。利用枠を取得するツールが提供されていれば、通常利用の可否・該当枠・追加クレジット消費の有無を確認する。取得ツールがないことだけを理由に止めず、既存契約内で通常実行できる内蔵ツールの判定に従う。未取得の残量を推測したり確認済みと報告したりしない。実際の利用上限・アクセス拒否・追加支払い・追加クレジット消費の案内が出たら停止し、APIキー方式・追加購入・別アカウントで回避しない。対象1記事につき各実行1回まで、各回最大3記事の内数とする。本人が候補のやり直しを明示した場合は自律的な同条件再試行と区別し、旧候補と不採用理由を保持した新しい改訂identityで、追加費用0円の範囲内で指示された修正を1回実施する。失敗や不合格の後は同じ条件を毎時再試行せず、具体的な改善仮説または利用可能状態の変化がある時だけ再検討する。生成済みの原PNG/JPEG・未統合PR・実行中ジョブを先に確認し、取り込み待ちを再生成で埋めない。

人物の継続起用や既存候補の具体的な修正では、[人物・衣装の正本](EDITORIAL_LOOP.md#成人の軽い未来企画既存枠)にある基準画像からの編集を先に検討する。入力は記事slug・現在の記事SHA・基準画像の実参照とSHA・今回変更する衣装/動作/背景/構図に絞り、固定設定や過去の全文ログを再投入しない。編集元を実表示し、参照元と新しい出力の来歴を別に保存する。新しい顔の採用は明示的な改訂として扱い、人物一致の検品を省略しない。

現在の本文に合う撮影可能な一場面を指示し、原PNGと取り込み後JPEGを実表示して検品する。新規生成・参照編集とも[内蔵画像の保存手順](NATIVE_IMAGE_BYTES.md#preferred-path-capture-generation-and-save-the-candidate-in-one-execution)の`native_image_stage.js`の`generateAndStage`に一本化する。同じ実行の同じ取得経路で既存の小PNGを読み、変換・GitHub保存・branchからのSHA読み戻しを通してから生成する。保存済み候補を先に回収し、既存の生成claimを消して同じ論理実行を再生成しない。ローカルパス/file IDの場合は、その実環境からバイトを返せる道具が必要で、data URL経路の成功や別runの成功を代用しない。経路不在・事前検証失敗なら生成を直接呼ばず、適合する代替で公開作業を続ける。原PNG・JPEG・実際の指示を保存し、失敗時は生の返値・転送済みPNG・checkpoint・claimの実参照を区別して同じ素材を回収する。候補保存、目視採用、本番反映、定期worker自身の完走はそれぞれ実確認で判断する。

`origin: chatgpt-imagegen`、実際の生成物の識別根拠、原PNG/JPEG SHA、指示、現在の記事SHAを保存する。実際のツール出力ファイル名のUUIDと、PNG内C2PA claimのasset instanceIDは区別し、未取得のbackend job IDを捏造しない。C2PAから取得した場合はその根拠を記し、署名・証明書を検証していなければ検証済みとは書かない。旧CPU候補の原生成記録・正確な整数seed・不採用理由は履歴に保持する。`visual_strategy: cpu-photo` と現SHAの`accepted`は、新JPEGの実画像・本文・scene_promptの一致を確認した同じ変更で記録する。写真が未完了なら適合する代替を維持し、イラスト掲載や生成成功だけで実写化完了としない。追加の外部API契約や有料GPUを導入しない。

写真が使えない場合、本文に合う専用SVGを `assets/editorial-scenes/` に用意する。`reviewed_story_scene` は記事指紋、主題、寸法、アクセシブルな説明、外部依存のないSVGを照合する。追加・修正時は `python3 scripts/social_cards.py --prepare-scenes 記事slug` で共有用PNGも用意し、実表示する。既定は既存の `rsvg-convert 2.62.1`。同じ版を使えない環境では、導入済みの `CairoSVG 2.7.1` を `--renderer cairosvg` で明示的に選べる。実際の描画ソフト名・版と記事・SVGの指紋をPNG内へ記録し、この2種類以外の描画ソフトや版は採用しない。同じ原本の検証済みPNGはどちらで作ったものも再利用し、通常ビルドは整合するPNGをコピーするだけで描画ソフトを起動・importしない。記事変更後に古い挿絵を自動流用しない。未検品・不合格のJPEGとその派生動画はHTML・OGP・RSS・配布対象から外し、安全なイラスト／承認済み素材で記事閲覧を続ける。

`visual_strategy: "illustration"` は「画像処理失敗」ではなく意図的な編集判断として扱う。2026-11-06 22:00 JST以降の新作では `illustration_reason` も必要で、`readable_text_or_ui / precise_count_or_absence / complex_relationship / comparison_layout / brand_character_safety` のどれかに限る。単一人物・単一物体・単純な行為で成立する場面は写真を既定とし、**写真向けの scene_prompt を書いたまま illustration に振り分けない**。`editorial_mix.py --day` は一日の `cpu-photo / illustration` 件数と `visual_next` を出し、イラストが過半になった日は次の候補で写真向きの場面も比較する。ただし題材の質を落として写真比率を合わせない。

`visual_review.py` の `strategy_counts` と各行の `visual_strategy` で区別し、専用SVGの欠落に加え、`editorial_social_png` が示す共有PNGの欠落・失効も `attention` で回収する。CPUを再起動して解消しない。

## 本文内の補助解説図

必要性と表現は[EDITORIAL_LOOP](EDITORIAL_LOOP.md#必要な記事には小さな解説図を添える)で判断する。記事の主要写真を保ち、採用した記事では`assets/article-diagrams/<slug>.svg`を1枚だけ本文1段落目の後に表示する。写真用の`visual_strategy`・scene_prompt・生成manifest・acceptedを、図の追加だけで変更しない。既存の写真代替用`editorial-scenes`と、文字付きの補助解説図を取り違えない。

SVGのルートは`xmlns="http://www.w3.org/2000/svg"`、`role="img"`、`viewBox="0 0 幅 高さ"`を持ち、`data-article-sha256`に現在の`generated_photos.article_fingerprint(article)`を記録する。直下の`title`は短い図題、`desc`は見えない場合にも物と関係が伝わる代替説明とする。`title`が図の下、`desc`が画像の代替テキストとして表示される。外部素材・スクリプト・HTML埋め込みを使わず、ラベルと関係を編集できる小さなSVGで作る。

`scripts/article_diagrams.py`が本文指紋・SVGの構造・自己完結性を検証し、現在の本文に対応する図だけをビルドで配布する。URLには実SVGのSHAを付ける。図なし・失効・不正な図では記事本文と写真をそのまま表示する。`visual_review.py`の`article_diagram`と`article_diagram_counts`で`absent / current / stale / invalid`を区別し、`stale / invalid`だけを既存の`attention`で回収する。`absent`は図がないという意味であり、図の必要性を自動判定した結果ではない。機械的な合格も内容の目視確認の代わりにならない。

全体の未完確認は`python3 scripts/visual_review.py --compact`で集計・`attention`・`photo_followup`を読む。省略するのは`images`詳細配列だけで、検出対象やエラーは減らさない。対象を決めたら`python3 scripts/visual_review.py --slug 記事slug`で詳細を取り、公開文全文と実画像を照合する。複数なら`--slug`を繰り返し、対象はOPERATIONSの上限内に収める。未知のslugは正常な空一覧とせずエラーにする。引数なしの全件一覧は既存の横断確認で使う。補助図の失効は現在の全文と実図を再確認して直し、指紋だけを更新しない。正常な主写真が採用されている記事の古い写真代替SVGは、状態を残したまま通常の修復対象から外す。補助図の不具合は主写真が正常でも別に回収する。

公開時は、既存の`check_live.py`が確認対象の記事について、本文内の図の有無・URL・説明・配置と、実配信SVGの内容を現素材と照合する。HTTP成功だけ、図のファイル保存だけで公開完了にしない。通常の公開検証の対象外にある既刊を変更した場合も、変更した記事と図の実配信は担当が直接確認する。

発行・改稿・公開後レビューの既存担当が、必要な記事だけ全文と図を照合し、スマホ360/390px程度とPCでラベル・物の位置・矢印・はみ出しを実表示して確認する。公開後は対象記事とSVGの実配信まで確かめる。本文が変われば図は失効するため、実物と新しい本文を再確認し、必要な修正を済ませた場合だけ指紋を更新する。新しい定期タスクや生成API、解説図だけの台帳は作らず、変更のない図を毎回作り直さない。

## 選抜動画の確認

選抜記事を変更した発行・改稿担当と、画像を検品するサイト担当は、既存の枠で `python3 scripts/publish_motion_clips.py --plan` を確認する。状態と次の作業は[MOTION_CLIPS.md](MOTION_CLIPS.md)に従い、未解決分を既存の結果・引き継ぎへ「slug／待ち理由／次の作業と担当」で残す。OFF時の空一覧は未処理なしを意味しない。

`visual_review_required` は現在の実画像を本文と照合し、上の採用条件で記録する。`image_required` は品質保留も含むため `scripts/visual_review.py` で詳細を確認する。`captions_required` は発行・改稿担当へ本文と3字幕の再確認を渡す。サイト担当が字幕の指紋だけを更新したり、未目視の承認を作ったりして解消しない。改稿担当は本文を直した後の字幕も読み直す。

準備完了・生成済み・本番配信済みを分け、待ち理由は読者画面へ出さない。既存の自動生成で進め、タスク・時刻・OFF設定・選抜の目安や生成上限を変えない。

## 表示確認と公開の完了

日次は変更箇所と新着を重点確認。週次は一面、一覧、記事、保存一覧、連載、発行号を確認する。スマホ360/390px・中間768px・PC1280px程度を使い、横はみ出し、見出しの折返し、画像切れ、余白、動画選択、タップとキーボードの操作位置を実画面で見る。エラー・空一覧・保存済み・画像代替など、変更に関係する状態も確認する。

専用の場面イラストは一覧の小さい枠でも構図全体を保ち、左右にいる人物・道具を切り落とさない。ブラウザ用favicon（PNG・ICO）とiPhone用アイコンは記事画像の採否と別に確認する。`scripts/check_live.py` がHTMLの宣言、3つの公開URLの形式・寸法・MIME・原本との一致、公開robotsのGoogle検索クローラー向け許可を検査する。HTTP 200や記事の配信成功だけでアイコン正常と判断しない。Google検索結果への反映は別に確認し、未確認なら復旧済みと報告しない。再取得待ちの間もアイコンURLは固定し、無意味な差替えやインデックス登録リクエストの連打をしない。
