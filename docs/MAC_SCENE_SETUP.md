# Macでの実写コント画像生成

GitHub側のコードだけではMacにモデルは入りません。画像がなくても、承認済み写真またはSVGで毎日の発行は続きます。外部の画像API・有料GPU・追加ChatGPTクレジットは使用しません。

## 停止・再開・状態確認（既存Mac向け）

導入済みモデルとvenvを再利用します。デスクトップの **未発生新聞画像生成** フォルダにある次のファイルをダブルクリックできます。

| ファイル | 動作 |
| --- | --- |
| `画像生成を停止.command` | Macの画像生成だけを停止。実行中の専用処理とlaunchdを解除し、再起動後もOFFを維持 |
| `画像生成を再開.command` | 初回3枚の確認記録を検証して未生成分の自動運転を再開。全停止で無効化したCPU画像ワークフローも元の状態へ復旧 |
| `画像生成の状態確認.command` | ON/OFF、実行中、成功・エラー、画像数と未処理数、容量、GitHub最終反映結果を表示 |
| `全画像生成を停止.command` | Mac側と、GitHubの `free-cpu-scenes.yml` だけを停止。該当する実行中ジョブもキャンセル |

ターミナルではリポジトリ内で以下を実行します。ほかの記事発行・漫画・GitHub Actionsは停止対象に含めません。

画像回収担当チャットの定期確認も停止範囲に従います。Macだけの停止ではCPU成果物の検品・公開を継続し、全停止では変更・生成・公開を行いません。状態JSONの`stop_scope`は`mac`・`all`・`unknown`、停止ラッチなしは`null`です。旧形式などで停止範囲が不明な場合も回収は読み取りだけにします。回収の担当と実行枠は[OPERATIONS.md](OPERATIONS.md)を参照してください。

~~~bash
python3.11 scripts/mac_scene_control.py status
python3.11 scripts/mac_scene_control.py stop
python3.11 scripts/mac_scene_control.py resume
python3.11 scripts/mac_scene_control.py stop-all
# GitHub CPU画像ワークフローだけを明示的に復旧
python3.11 scripts/mac_scene_control.py resume-cpu
# ショートカットを作り直す
python3.11 scripts/mac_scene_control.py install-shortcuts
~~~

停止は専用アプリ領域の `stopped.json` に永続化します。ワーカー起動時、生成前、push直前に確認し、明示的な再開まで新しい処理を始めません。停止時はPID・起動日時・UID・実行パス・専用プロセスグループを照合し、他のPythonや一般のComfyUIを一括終了しません。モデル・保留画像・既存記事は保持します。

停止要求の直前に既に送信中だったpushはGitHub側で完了する場合があります。その場合も完了SHAを記録し、次回の再開で最新mainと照合します。停止後に新たなpushを始めることは防止し、成功分のoutboxを消しません。認証不足や通信障害でGitHub CPU側を止められなければ、エラーと対象を表示し、成功扱いにしません。

自動実行は毎時45分とログイン時、標準は1回1枚。手動指定も最大4枚までです。Macがスリープ・電源OFF中は処理できず、復帰・ログイン後に未処理分を確認します。常駐のComfyUIは残さず、処理終了・停止後に専用サーバーと不要PNGを片付けます。生成中は12GiBの空き、1枚700KiB・生成JPEG総量1.5GiBの上限を維持します。

各回はモデルの確認より先に、最新mainを取得し、保存済みoutboxの再送と未処理記事の確認を行います。承認済み画像または品質保留により生成対象が0件なら `idle` で終了し、モデル全体のSHA検査も専用ComfyUIの起動も行いません。保存済みJPEGの再送にはGPUを使わず、Macのメモリプレッシャーが高い場合も再送できます。ディスク空き容量と永続OFFの確認は引き続き適用します。

最新mainの取得・画像再送に失敗した場合は新着なしと判定せず、モデルを起動せずにエラーを記録して次回へ持ち越します。この事前同期も専用プロセスグループへ登録し、実行中の停止要求や期限超過で安全に終了します。`idle` は新しい画像生成の成功扱いにせず、過去の成功日時と実エラーを保持します。

## Macの負荷保護

画像の処理速度よりMacでの作業を優先します。ComfyUIを起動する前と、起動・生成中に約10秒間隔でOSの状態を確認し、次のいずれかならその回の画像生成を見送ります。

- メモリプレッシャーが警告・危険、または`memory_pressure -Q`の空き割合が20%未満。
- Mac全体の使用スワップが4GiB以上。
- OSがCPU・GPUの速度やCPUスケジューラを80%未満に制限する、または温度警告を報告。
- メモリ状態の取得失敗。未確認のまま重い処理を始めません。

途中で条件を超えた場合も専用の子プロセスだけを終了し、保存済みJPEG・outbox・モデルは保持します。負荷による見送りは`resource-paused`として記録し、成功履歴を消しません。自動運転がONなら次の毎時45分に再判定します。手動の「停止」は従来どおり永続OFFであり、負荷回復だけで再開しません。スワップはOSが管理し、生成終了後もすぐ減らないことがあるため、見送りが続く場合があります。

専用ComfyUIはCPU計算のスレッド数を2に抑え、プレビューを無効化し、メモリ予約の余裕を指定します。専用の子プロセスだけにPyTorch MPSの上限比率`0.8`、回収開始比率`0.7`を設定します。これはMPS割り当ての上限であり、Mac全体のメモリ上限ではありません。上限に達して画像生成に失敗しても記事は代替画像で公開を続けます。一般のComfyUIや他アプリの環境設定は変更しません。

「状態確認」には最後に測定した負荷・スワップ・見送り理由と確認日時を表示します。Macの再起動、他アプリの終了、他アプリのキャッシュ削除、OSのスワップ削除は自動では行いません。これらの保護は負荷を抑えるもので、OSや他アプリを含む無停止を保証するものではありません。

目視で題材が不一致だった記事はmanifestの `rejected` に記事のSHAを記録し、同じ内容のまま自動再公開しません。記事本文や場面指示を直すと保留が解除され、明示的な `--force` でも再試験できます。保留中も写真／SVGで記事公開を継続します。

ワーカーの生成・同期成功と、読者向けの画像採用は別です。新規JPEGの機械検証は従来どおり行い、公開ビルドではさらに`content/visual_reviews.json`の目視確認を記事・画像のSHAと照合します。未検品のJPEGを保存しただけで掲載成功とは扱いません。Macの稼働状態は実機で確認し、リポジトリ更新だけで稼働・反映を断定しないでください。検品担当と手順は[VISUAL_OPERATIONS.md](VISUAL_OPERATIONS.md)を参照。

画像は**実写の報道写真・現場スナップとして見えることを必須**にします。アニメ調、イラスト調、3DCG、ゲーム画面風、プラスチック肌、広告写真・映画ポスターのような過度な演出は、題材や構図が合っていても生成写真として不採用です。風刺は画風を奇抜にせず、普通の場所・人物・照明の中で起きる状況そのもので見せます。機械検証は破損・寸法・容量・SHA・記事対応を確認し、実写感・小道具・オチの一致は[VISUAL_OPERATIONS.md](VISUAL_OPERATIONS.md)の目視ゲートで判定します。初回3枚の実生成・目視・本番配信確認を記録した `quality-pilot.json` がない状態では再開できません。

GitHub CPUルートは記事更新時と毎時17分に不足分を処理し、Macが負荷保護で待機中でも進めます。Macの「画像生成を停止」はMac側だけ、「全画像生成を停止」はこのCPUワークフローも無効化・キャンセルします。「状態確認」は最新mainの画像数とCPU直近ジョブを取得し、通信失敗でキャッシュ参照になった場合は明示します。CPUのジョブ成功だけで新画像の生成・本番公開成功とは扱いません。詳細は[FREE_CPU_IMAGES.md](FREE_CPU_IMAGES.md)を参照してください。

## 記事ごとに異なる場面

各記事の `scene_prompt` に、本文のオチを視覚化する英語30〜70語（800文字以内）の具体的な場面を保存します。人物の動作・小道具・場所を指定し、文字・ロゴ・実在人物を入れません。記事自動発行時にこの項目も執筆し、Macは画像生成だけ行います。指定がない旧記事は既存の場面テンプレートを使います。

本文・見出し・要約・場面指示が変われば旧画像は無効となり、次回に生成し直します。画像の解像度、形式、サイズ、SHA-256、記事との対応を検証します。真っ黒などほぼ単色の生成物も拒否します。ただし、人物の手・文字の混入・笑いの分かりやすさは機械検証だけでは保証できません。初回の実生成は目視確認してください。

## 競合・障害からの復旧

1. 最新mainをfetchし、専用の一時worktreeを用意。
2. 以前の成功画像を再送してから、画像のない記事を標準1本（手動指定は最大4本）生成。Macの負荷が高ければ生成を見送る。
3. 成功画像を専用outbox `VeripsaScenes/pending` に保管。一部失敗しても成功分を反映。
4. push直前に再び最新mainを取得し、内容が一致する画像とmanifestだけを合成。記事追加・他の画像を維持。
5. 通常pushが競合したら最大3回再試行。失敗した画像は次回へ持ち越し。force pushはしない。

ユーザーの作業ブランチ・未保存変更・記事本文には触れません。強制終了で残った専用worktreeも次回に復旧します。記事本文が生成中に編集された場合は古い画像を公開しません。通信障害時も既存写真／SVGで公開を継続します。

Macが停止中は生成できません。ログイン直後と毎時45分に不足分を再確認します。各処理後に専用ComfyUIを終了し、PNGを片付けます。launchdが引き継がないHomebrew／gitのPATHも設定済みです。

タイムアウト・容量不足時はその回の残りの画像をキューへ追加しません。launchdからの停止要求でも子プロセスを終了し、専用PNGを片付けます。セットアップ・生成・キャッシュ削除は同時実行を防止しています。push競合で最新mainを再取得するときも、増えたJPEG分の容量を確認します。壊れた再送用manifestは上書きせず保存し、本番確認では画像のSHA-256も照合します。

## 停止と診断

~~~bash
# スケジュール停止。モデル・記事・JPEGを保持
python3.11 scripts/mac_scene_setup.py --disable-schedule

# 専用の一時キャッシュだけ削除。実行中は拒否
python3.11 scripts/mac_scene_setup.py --cleanup-cache

# 生成予定を確認（モデル、通信、GitHub書き込みは不要）
python3.11 scripts/local_scene_photos.py --dry-run --limit 3
~~~
