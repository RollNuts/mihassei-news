# 未発生新聞｜継続改善の編集ループ

このメモは発行・日次点検タスク向け。公開サイトの読者画面には載せない。**1本の面白さを先に改善し、新機能を増やさない**（特に2026年11月3日〜9日の7日間）。追加課金、外部AI API、画像API、広告費、新規管理画面は不要。

## ① 書く前｜直近の弱点を引き継ぐ

- `content/articles.json` の**直近20本**を実際の `published_at` 順で確認し、見出し、元ネタ、冒頭、最後の一文、カテゴリ、笑いの仕組みを比べる。公開日の偽装はしない。
- `python3 scripts/audit_satire.py` の `NEXT SLOT (advisory)` と `::warning` を参考にする。自動チェックは文章の表面の反復を見つけるだけであり、面白さを採点するものではない。
- 前の1〜3枠の見出し・末文と同じ逆転（AIが選別、申請が無限、謝罪、担当者の一言）を避ける。元記事が変わっても同じオチなら発想を変える。
- 本当に公開された**当日の新しい一次情報または信頼できる報道**を探す。公開日時、記事内容、元の文脈を確かめる。検索結果の日付だけを信じない。SNSのトレンド規模や炎上数を捏造しない。

## ② 書くとき｜見出し→現場→別のひねり

1. 「今の何が滑稽か」「5年後にどこだけ行き過ぎるか」「一番おかしい具体的な行動は何か」を1行ずつ用意。
2. **仕組みの違う見出しを2案**作る。3秒で異常さが分かる案を採用し、元ネタを知らなくても読めるようにする。
3. 冒頭は会話・行動・場面を優先。架空企業の発表や制度説明は必要な分だけ。短報は2段落180〜350字を目安に、必要なら3〜6段落。段落数で水増ししない。
4. 本文の後半には**見出しに書かなかった2回目の逆転**を置く。末文を「担当者は困惑」「検討している」で逃げず、誰かが実際に何をしたかで閉じる。自然に余韻が残るなら台詞でもよい。
5. 表面的な言い換えではなく、人物の誤解、善意の暴走、皮肉な成功、ファン文化、日常の小さな矛盾、言葉遊びなど笑いの構造を変える。政治・社会の論争も事実と創作を区別し、実在する私人への攻撃はしない。

## ③ 公開するとき｜公開できる物だけ

- 出典URLと`source.published_at`を検証。架空記事にはフィクション表示。 `fiction_at` は元情報の5暦年後。`published_at` は初回公開の実際のJST日時で、改稿時は`modified_at`だけ更新。
- JSONとリンク・本文の整合性を確認し、既存のGitHubテスト、公開サイトのSHAと記事表示を可能な範囲で検証。コミット成功と本番配信成功を混同しない。
- **毎日9枠の発行努力目標は維持**。警告を理由に無投稿にせず、候補を変えて短くても独自の作品を目指す。出典・安全・ツールの実際の制約で発行不能なら正直に報告。
- 新規の有料サービス、AIトークン課金、有料プランへの移行、アクセス水増し、Xへの大量自動投稿はしない。

## ④ 次の発行へ｜小さく学ぶ

- 各枠の終了時に「今回は前回と何を変えたか／次枠は何を変えるか」を**各1行**残す。記事URLと公開済みか未確認かも残す。報告は編集メモであり、閲覧者向けの記事に書かない。
- 日次点検では直近6〜20記事を振り返り、**一つだけ**次枠への編集方針を提案。繰り返し減少を確認できたら次の仮説へ進む。
- `analytics/daily/` の計測値は累積の匿名ブラウザ識別子で、PV、実人数、閲覧時間、面白さの証明ではない。標本が少ない間は数値で「改善成功」を断定しない。日次の増加や元記事ごとの滞在時間を想像しない。
- 2026年11月10日に11月3〜9日の短報、テーマ、オチと**確認できた範囲の**反応を振り返り、次週の編集方針を一つだけ見直す。新機能を増やす判断はその後。

この運用は外部のLLM API・GitHub Actionsの追加トリガー・新規DBを必要としない。警告スクリプトは助言のみで、発行や記事表示を止めない。
