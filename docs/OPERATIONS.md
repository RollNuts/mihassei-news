対象は [未発生新聞](https://veripsa.com) と `RollNuts/mihassei-news`。各タスクはこの共通手順と担当分の資料を読み、同じ規則をプロンプトへ複製しない。改善履歴はPR・コミットに残す。

## タスク間の優先順位と変更権限

複数タスクが同じ時間帯に動いても、担当外の改善を取り込んで仕事を広げない。各タスクの自動化プロンプトはこの節を参照し、ここにある規則を全文複製しない。

1. **未完了の復旧が新規改善より先。** 同じ記事・PR・配信・画像に未完了があれば、次のタスクは別の修正を重ねず、既存担当の完了状態を確認する。重大な本番障害・CI回帰は例外として最優先で直す。
2. **記事発行は新作1本の品質と公開を担当する。独立した初読を同じ実行で行えない場合は、同じPRの初読と公開を既存の公開後レビュー担当へ明示的に移譲する。** 全体ルール、Automations、X設定、週次方針を各発行枠で変更しない。公開後の最初の「次の記事」は、自然な共通タグを持つ古い記事があれば関連話題を優先し、なければ時系列で進む。タグは回遊のために捏造せず、本文に本当にある持続的な題材だけを再利用する。
3. **日次編集は前日の全公開文の再読、必要な既刊の改稿、次候補を担当する。** 読み取りに迷う原文を具体化し、意味の理解を妨げる箇所の修正を最優先に、既刊改稿は1〜2本までとする。具体的な判定・記録はEDITORIAL_LOOPに従う。全体の配分・スケジュール・Xの配信方式を毎朝変更しない。`page_views_per_hour` と `continuation_share` は補助指標として使い、少数例から当たり型や回遊施策を確定しない。
4. **週次編集だけが継続ルールを見直す。** 7日分の実測と実文を比べ、翌週に変えることは原則1つ。緊急障害を除き、複数の編集ルール・配分・運用を同時に変えない。
5. **公開後レビュー・画像回収は、明示的に引き継がれた未公開PRの初読と公開、新着の理解と写真の完了を担当する。** 発行担当は、独立した読み手を使えない場合にPR本文の既存欄へ「初読待ち／変更担当reviewer／slug／現head／記事SHA／元run ID」を残し、以後は同枠の再試行でも書込み・新生成・mergeを止める。reviewerはmain差分0でもこのPRを優先し、公開予定文だけの初読を作者の説明より先に行う。必要な修正・再読・最新headのCI・安全な統合・本番確認は同じPRで引き継ぐ。初読が未完了なら担当を維持して次の既存枠へ渡し、paused/in_progressだけで担当を戻さない。通常の新着・改稿・明示未完了も、公開文だけで主語・動作・因果・時間順・見出しとの一致を確認する。EDITORIAL_LOOPの既存6点に従い、理解を妨げる具体的な箇所だけを直して再読し、本文を確定してから写真を扱う。題材・出典・編集レーン・自動化・X設定へ広げない。修正不要な本文と正常なaccepted画像は変更せず、各回最大3記事で未完了を優先する。
6. **X自動投稿担当は記事紹介レーンだけを担当する。** 記事本文や発行スケジュールを直してX枠を埋めない。配信障害はsocial-bot側で直し、反応が弱いだけなら単発データで選定規則を書き換えない。
7. **実測は役割別に読む。** 日次PVはサイトの動き、`page_views_per_hour` は公開年齢差を少しならす補助、`continuation_share` は記事から別記事へ進んだ粗い回遊、`x_arrivals` / `search_arrivals` は入口の補助指標。どれも実人数・読了・満足度・因果の証明にはしない。

定期タスクの予定時刻はAutomationsを正とし、文書やプロンプトへ同じ時刻表を重ねて保守しない。時刻変更が必要な場合だけAutomationsとこの表を同時に更新する。
## 着手と公開

1. 最新main、`AGENTS.md`、自分と関連担当の直近結果、未統合PR・実行中CIを確認する。前回の未完了作業を先に片付け、同じ記事・ファイルの重複PRを作らない。コマンドを使う前に、下記「実行環境の準備」で今回の実行環境へ入力ファイルを用意する。
2. 発行は予定枠のJST日時と既刊・PRを照合する。**1枠1本、JST1日通常7本を基準・最大9本**とし、同じ枠で公開済み記事・未統合PR・公開待ちが1本でもあれば、その枠に別記事を追加しない。遅延や再試行を別枠として二重発行せず、未完了分を先に復旧する。改稿はslug・出典・元資料の日付・架空日・初回公開日時を保持し、`modified_at`だけ実際の更新日時にする。
3. 新作・改稿の原稿は、画像生成前にEDITORIAL_LOOPの「公開前の6点」で読み直し、理解に迷う箇所を解消してから次へ進む。専用ブランチで必要な変更と回帰検証を行い、PRの最新headのCI・履歴保護を通す。統合直前に最新mainと並行変更を再確認し、独立した初読と必要な修正・CIを終えた現担当が安全に統合する。失敗の無視、強制統合、force push、テスト無効化はしない。
4. 本番revisionと対象URL・画像等の実配信を照合する。PR作成、CI成功、main統合、実配信を区別し、未反映は既存権限で原因を調べる。静的プレビューのAPI未接続を本番障害としない。
5. 読み取り検証か `?analytics=off` を使い、確認操作を読者のPVとして成果に含めない。画面・実画像を見られなければ未目視と記す。

公開する内容がない点検では、理由を短く残して終了する。PR数、規則の追記数、生成数、同じ障害の再報告を成果にしない。

### 実行環境の準備

別チャットの作業パスや前回の一時ファイルは、今回も存在するとは限らない。最初に今回使えるコード実行・ファイル書き込み手段と作業場所を確認する。専用checkoutがある場合は、実際のHEADが取得した最新mainの完全なSHAと一致すること、作業ツリーと必要ファイルの実在を確認し、他担当の変更を上書きしない。改稿の検証ではそのmainから作った担当ブランチの変更内容も確認する。

**配分確認は、checkoutがなくても次の2ファイルを実配置してから実行できる。** GitHubで内容を読んだだけでは、実行環境へ配置したことにはならない。

1. 最新mainの完全なSHAを1つ取得し、そのSHAに固定して `scripts/editorial_mix.py` と `content/articles.json` をGitHub接続から取得する。Contents APIなら `https://api.github.com/repos/RollNuts/mihassei-news/contents/<path>?ref=<完全なSHA>` を使い、2ファイルを異なるrevisionから混ぜない。
2. 取得したUTF-8文字列を、利用可能なファイル書き込み手段で今回の専用フォルダーの `scripts/editorial_mix.py` と `content/articles.json` へそのまま保存する。コード実行内で取得結果を捕捉できる場合は、文字列をモデル本文へ転記せず `apply_patch` 等へ直接渡す。JSONを再保存して整数や内容を変えない。
3. 同じ実行環境で2ファイルの実在を確認し、そのフォルダーを作業場所にして `python3 scripts/editorial_mix.py --check --day YYYY-MM-DD` を実行する。日付は今回の予定枠のJST日付。終了コードと `desk_next`・本数・分類の実出力を残す。ファイル不在なら配置を直してから再実行し、不在のまま同じコマンドを繰り返さない。

この2ファイル構成は配分確認専用で、完全なcheckoutではない。`visual_review.py`、本文差分、放送室の `--health` / `--plan` は関連モジュール・設定・画像等も読むため、必要な内容がそろった専用checkoutで実行する。そろわない場合は、GitHub接続で現在のソースと該当する既存Actionsの実結果を確認し、直接実行・Actionsでの確認・未確認を分ける。放送室は既存 `auto-motion-clips.yml` のvalidate jobにplan/healthがあるが、取得したrunの実checkout SHAと関連入力を照合し、古い結果を現状態にしない。状態確認のために生成・publishを起動しない。

実行手段自体がない場合は、ファイル不在と区別して不足する能力を示し、GitHubで可能な差分・採否・候補回収を続ける。準備手順の追加や別チャットでの成功だけで定期workerの復旧済みとはせず、実際の次回runの結果で確認する。

### 本番確認の代替経路

タスクの実行環境から本番へ直接接続できない場合は、既存の読み取り専用 `.github/workflows/verify-public-photos.yml` の実行結果をGitHub接続から回収できる。新しい監視タスクを作らず、次の証拠をそろえる。

- 対象main SHAのrunは `https://api.github.com/repos/RollNuts/mihassei-news/actions/runs?head_sha=<完全なSHA>&event=push&per_page=20` から探し、workflow path・head SHA・jobを照合する。`fetch_commit_workflow_runs` はPR実行限定のため、この本番push確認には使わない。既知の手動runがある場合もその実SHAを確認する。
- jobの実stepが成功し、ログの本番revisionが対象SHAと一致することを確認する。docs-only祖先を許容した結果なら、その差分証明も残す。run全体のsuccessやPRのCI成功だけで完了にしない。
- 対象slugの `Public article OK`、変更した画像・図の検証結果、必要な共有画像の対象を確認する。現行 `check_live.py` の本文確認は最新10記事、`check_share_cards.py` は選抜したカードの確認であり、対象外まで検証済みにしない。ログに含まれない対象や変更素材は、直接の取得・対象を指定した検証・次担当での確認を未完として残す。
- 結果は「Actionsで実配信検証済み」と「今回のブラウザ目視」を分けて記録する。取得不能・実行中・対象外を0件や本番障害へ読み替えない。取得不能なら失敗した取得操作を残し、実行中なら同じrunの完了を確認する。対象外は対象を指定した検証へ引き継ぐ。

同じworkflowの末尾にある `Report photograph completion separately from delivery checks` は、checkout SHAに対応する画像選択・写真待ち件数・対象slugと次の操作をSummaryと `live-photo-health-<run_id>` artifactへ出す。記事・共有カードの配信結果と写真の完了を別々に読む。`photo_followup_counts` は写真向け記事だけの未完了で、意図的なイラストも含むJPEG全件の `missing` とは異なる。これは現素材の選択結果であり、新しい目視採用や全記事の本番表示確認ではない。正常な代替画像での公開は継続し、写真待ちは既存の回収担当が引き取る。

## 画像・動画の担当を重ねない

- 発行・改稿担当は**自分が今回変更した記事**の画像と選抜字幕を確認する。ほかの記事の検品在庫を各発行枠で毎回取り直さない。
- 公開後レビュー・定期画像回収の主担当は、既存ChatGPTタスク `6aec3e2245448191b8ae17c80deb5008`。GPTのrunが終了し、画像の保存・採用・公開が未完了で担当PRがない対象だけ、既存Codex automation `automation`（対象チャット `01a19f75-bfe8-7f72-9d02-eb0f936a9de3`）が画像復旧を引き継ぐ。GPTの実行中・変更担当PR・未完了の生成claimがある間は重複生成しない。復旧PRを開始した対象は、そのPRを完了するまでGPT側も再生成・別PRを作らない。通常の記事・初読の担当は移さず、利用枠の回復だけを理由に再生成しない。実際の登録・停止状態は別途確認し、文書更新だけで設定完了とは報告しない。
- この担当が発行予定枠のおよそ25分後と次の毎時枠で未完了を引き取る。記事発行担当は自分の記事の写真を公開PRへ同梱することを優先し、取り込み未完了なら生成物の実際の保存先・取得参照、記事SHA、止まった段階、次の操作を渡す。発行担当がまだ変更を続けるPR・生成・本番反映には重複作業をしない。初読の移譲が明示されたPRはreviewerが同じ成果物を引き受け、publisherの実行状態表示だけで待ち続けない。生成済みPNG/JPEGがあれば新規生成より回収・変換・検品を先に行う。次の記事発行まで待たせず、過去枠の回収を発行担当と重ねない。

## 維持する境界

- 追加費用0円。有料AI・画像・動画API、GPU、追加クレジット、有料データ、広告、新規従量課金、有料プラン変更はしない。
- 記事の既存9枠、承認済みX配信、既刊、正史、予測条件、読者データを維持する。担当外の投稿・予約・台帳・他タスク・実行時刻・OFF設定を変更しない。停止中の漫画・旧シュールネタ・ネタ画像を再開しない。
- Macの稼働は実機の状態で確認する。コードや設定済みというだけで稼働と断定せず、停止・負荷・容量保護を解除しない。
- PVは表示回数。匿名ブラウザ数・実人数・読了・面白さ・Xインプレッションとは別。時点・対象期間・経過時間・単位を添え、未取得や計測開始日の一部を0や一日分にしない。少数データから改善の因果、収益、ファン獲得を断定しない。
- 読者画面は読む・探す・保存する・共有するための情報に絞る。内部手順、改善宣言、自己採点、運営者向け説明を載せない。創作表示、出典、必要な計測・保存説明は適切な案内ページに短く残す。
