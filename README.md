# 未発生新聞 — Mihassei Shimbun

**https://veripsa.com** · 5年後の架空ニュースと連載を届けるメディア。推理小説は創作、未来相場観測室は実際のデータに基づく市場考察です。

> 【重要】架空ニュース・推理小説の事件・企業・談話は創作であり、実在する人物・企業の架空の不祥事を描きません。別枠の「未来相場観測室」は公開資料の出典を示した市場分析と編集上の仮説で、予想は保証されません。創作と事実の境界を明確にします。

## 設計

- 静的HTML/CSS。Python標準ライブラリだけでビルド。記事は `content/articles.json` に保存。
- 1記事 = 1つの独立ページ・オリジナルのSVGイラスト・元の話題へのリンク。
- 発行日時は元ネタの掲載時刻（日本時間）に**5年を加算**。元の情報と架空の記事を別枠に表示。
- 検索・カテゴリ絞り込み・RSS・サイトマップ・スマートフォン表示。
- 記事の自動作成はChatGPTの定期タスクと接続済みGitHubで行う。外部のAI生成APIやAPIキーは使用しない。画像はAPI不要のオリジナルSVG。
- ソーシャル（Redditなど）の公開RSSも候補。Xや5chの本文・画像の無断スクレイピングはしない。許諾済みの公開リンクを使う場合は `content/source_seeds.json` へURL・日時・要旨を追記する。

 
## 独立連載：未発生事件簿／未来相場観測室（無料）

- 編集データは `content/serials.json` に保存。架空ニュース用 `content/articles.json` とは別の入稿ルートで、フィクションの日時・ニュース原典ルールを市場分析に誤適用しない。
- `/serials/` に連載トップ、`/serials/{series-slug}/` に連載ページ、`/serials/{series-slug}/{episode-slug}/` に各話の独立URL。トップとナビから読み進められ、未来の未公開ページへのリンクは表示しない。
- 推理小説は `kind: fiction`。すべてオリジナル創作、各話に読者の手掛かりを添える。次回公開は `episodes` に新しい話を追記し `number` を1つずつ増やす。
- 市場予測は `kind: analysis`。実際の根拠資料 `sources`、強気・中立・弱気 `scenarios`、反証可能な `forecast` と検証日を必須にする。価格や決算を未確認のまま断定しない。未来予測は投資助言・売買推奨ではない。
- `scripts/serials.py` がPython標準ライブラリだけで連載ページ、オリジナルSVG表紙、1200×630のOGP PNGを生成。独立canonical、Article構造化データ、サイトマップを付与。追加のAPI、外部有料モデル、画像生成課金、DBを利用しない。
- 続編追加後は `python3 -m unittest discover -s tests -v` を実行し、日付・検証方法・出典を確認する。市場見通しの正確さや広告審査・検索流入は保証されない。

## 発行状況と元ネタの鮮度

- トップの「本日の未発生ニュース」は、現実の日本時間で当日公開された記事があるときだけ表示する。号外の架空時計は5年後の演出で、リアルタイムのニュース速報を意味しない。
- 本紙の実際の最終発行日時と最新発行日の本数を元データから表示する。日付が変わるとブラウザ側で「最新の未発生ニュース」に戻る（すでに読み込んだ記事の偽更新はしない）。
- GitHub CIで`scripts/audit_editorial.py`を実行。直近48時間の原典が本紙掲載より12時間超前、ジャンル・AI題材が60%以上、日時に矛盾がある場合に警告する。**警告は出版停止条件ではない**ため、毎日の発行頻度を妨げない。新規API・課金・記事の自動没扱いはしない。

## 検索流入・次の記事・再訪を増やす改善（2026-11-03）
- 追加のAPI・外部サービスなしで、記事のタイトル・要約・元ネタの主題から明示的なトピックを判定。同じ話題の**他の記事**を提案し、関連記事カードと「次に読む」の重複を解消。関連性の薄い記事しかないときはジャンルと実際の掲載日でフォールバックする（検索品質やCTR・滞在率の向上は未実証）。
- 記事の構造化データに現実の掲載・更新日時と`mainEntityOfPage`を明示。発行号・既存の厚みのあるカテゴリページには、実在する記事だけの`ItemList`（先頭最大30件）を付与。発行号には検索クローラー向けの`BreadcrumbList`も加える。
- RSSは直近30本から**90本**に拡充して高頻度発行後も見落としを減らす。ジャンルも配信し、トップに「新着RSSを購読する」を配置。メール登録フォームや追跡ピクセルなし。
- サイトマップやcanonicalは維持し、検索登録・表示順位・実際のSNSカードやRSSリーダー表示は保証しない。既存の無料ホスティングのままで動作する。

## 日付で読む発行号（追加費用なし）

- 現実に本紙が公開した `published_at` の日本時間の日付から、自動で `/issues/YYYY-MM-DD/` を生成する。5年後の架空日時 `fiction_at` を実際の発行日と誤認させない。
- 同じ日に3本以上公開された場合だけ、個別の発行号を作る。1〜2本の薄いアーカイブページは生成・サイトマップ登録しない。
- `/issues/` から過去号を一覧でき、トップページには直近3号を案内。各記事からも同じ日の発行号へ戻れる。記事は実際の掲載日時順で並ぶ。
- 発行号のページは静的HTMLだけで利用可能。JavaScript・新しいAPI・課金DB・画像生成サービス不要。
- GitHub Actionsの公開後チェックは発行号一覧と、最新3号の記事リンク・サイトマップを読み取り専用で検証する。投稿が遅れた日の記事を「今日の新着」と偽って表示しない。

## 好きなジャンルの新着をRSSで購読（無料）

- 全ジャンルの記事を配信する既存の `/feed.xml` に加えて、実際に掲載記事のあるジャンルごとに `/feeds/society.xml`, `/feeds/economy.xml`, `/feeds/technology.xml` など7種類を上限として自動生成する。記事数ゼロのフィードは作らない。
- RSSリーダーを使う読者は、`/archive/#category-feeds` から選んだ分野を登録できる。記事が3本以上あるジャンルの固定アーカイブには、ページ内の購読リンクとRSS自動検出メタタグを設ける。
- RSSは現実に公開した `published_at` を利用して、新着順に最大30本。架空の日付を `pubDate` に使わず、写真素材は検証済みの自前JPEGか編集部制作PNGのみ。画像クレジットも既存の配信仕様を維持する。
- ジャンル別RSSのXMLは記事本文とは別の配信形式なので、サイトマップに追加せず、検索結果での記事本文との重複を抑えるため `X-Robots-Tag: noindex` を付与する。購読には影響しない。
- Python標準ライブラリの静的出力だけで完結し、追加のAPI、メールアドレス収集、有料通知サービス、課金サーバーは不要。登録者数や配信開封数を実測していると誤表記しない。

## 読者導線と編集方針

- トップページはジャンル別の入口を設け、記事数に応じて厚みのあるカテゴリ固定ページと記事一覧フィルターを使い分ける。
- 記事一覧は最初に18件を表示し、「さらに記事を見る」で18件ずつ追加。検索とジャンル・年代フィルタは未表示の記事も含む全件を対象とし、JavaScriptが利用できない場合は全記事を表示する。ホームの号外抽選データは新着40本までに制限し、記事量増加に伴う転送量の肥大化を防ぐ。
- 記事末尾の「続けて読む」は、タイトル・着想元の話題・記事要旨から保守的に同じ題材を選び、同程度なら実際の本紙掲載日が新しい記事を優先する。大きい「次に読む」と下の関連記事カードの重複・自己リンクを防ぐ。PV順位やAIによる意味理解を装わない。
- RSSへの購読導線と、記事・サイトをXで共有するリンクを設ける。未確認のSNSアカウントを「公式」として紹介しない。購読数やPVを実際より多く見せない。
- `/editorial/` で生成AI・自動化の利用、創作と出典の区別、広告と権利対応、連絡方法を公開する。編集方針は将来の運営変更に合わせて更新する。
- AdSense審査・広告収益は保証されない。承認前の広告スクリプトの自動挿入は行わず、広告導入時は読みやすさ・プライバシー・PR表示を優先する。

## Xのリンクプレビュー（無料で安定化）

- 画像の有無は記事内の写真表示とは別問題。OGP・Twitter Cardの画像はビルド時にローカルPNGを生成して配信する。外部API・課金画像生成なし。
- 2026年11月2日、Xの投稿画面が古いタイトルと画像なしカードを表示する問題を確認。無料のGitHubランナーから Twitterbot/1.0 UA としてHTML・画像を実測した結果、両方HTTP 200、適切なOGPと1200×630 PNGを確認。X自身の内部キャッシュは直接閲覧できない。
- Xが保持する古いカードを回避するため、トップの共有用リンクを `https://veripsa.com/?src=x-launch-20261102-v3` に変更し、トップのOGP画像を新しい固定パス `/og/brand-launch-20261102-v3.png` に変更した。 `/og/brand.png` は既存リンク用に継続配信する。
- Canonicalは `https://veripsa.com/` のままで、無意味な重複ページをSEOに増やさない。X側の再取得・実際のカード表示はXの仕様・キャッシュに依存するため保証はできない。
- ローカルテストでPNGのCRC・サイズ・展開後ピクセル数、X共有用URL、メタタグを検査。公開後もTwitterbot相当の読み取り専用検証を行う。

## 発行号の共有画像とX導線（2026-11-03）
- 1日に3本以上掲載した発行号には、実際の発行日ごとのオリジナル1200×630 PNG（`/og/issues/YYYY-MM-DD.png`）をビルドで作る。X・OGPには実在の事件の写真を使わず、**創作の新聞表紙**を配信する。
- 号ごとのページとトップの最新発行号に、読者が自分で押せる「Xで紹介」リンクを掲載。本文には実際の掲載日、見出し、フィクション表記、発行号URLを含める。自動投稿は行わない。
- 共有URLには流入把握用のUTMを付与するが、canonicalは元の発行号URLのまま。画像の取得可否・SNS上の表示は公開後のHTTP検証と各プラットフォームのキャッシュに依存し、表示を保証しない。
- SVGや外部画像APIをOGPに指定せず、既存Python標準ライブラリとCloudflareの静的ファイル配信のみで維持。無料運営を変えない。

## 新着記事のSNS画像（無料・自動）

- 写真がキャッシュ済みのページはライセンス検証済みJPEGを使用。写真が未設定の新着記事は`scripts/social_cards.py`が記事ごとに違う1200×630 PNGをビルド中に自動生成する。
- カードはジャンル名・架空年号・FICTIONラベル・内容種別に合わせたイラストで、架空事件の記録写真を装わない。日本語見出しはHTMLのOGP・Xタイトルとして配信する。
- Python標準ライブラリのみで動作し、外部API・フォント購入・生成AI API・追加の課金サービスは不要。公開URLも自動チェックする。

## 画像の品質を継続確認する仕組み（追加費用0円）

- 新着記事のX向け1200×630 PNGには、記事タイトルから判定した**電話・天気・野球・土産・ドラマ・情報保護などの題材に合うモチーフ**と英語の短い題材名を使う。見出しは引き続きOGPの日本語テキストで配信し、別途記事本文で見出し入りSVG表紙を表示する。
- 画像テンプレートを更新した際のX画像キャッシュ対策として、`/og/articles/<slug>.png?v=20261103-topic2` を新規共有のOGPに使用する。実ファイルは旧URLでも配信され、既存投稿のリンクが突然切れない。Xの実プレビューの更新や表示はX側のキャッシュに左右される。
- 記事ごとのX共有リンクに `utm_content=topic_card_v2` を付ける。Google向けcanonicalは従来どおりのシンプルな記事URLで、検索用の重複ページは生成しない。
- `/feed.xml` の各記事にMedia RSSの `media:thumbnail` と `media:content` を追加。無料の自前PNGか、編集部で承認した自前キャッシュ済みJPEGだけを指定する。写真には撮影者クレジットを記録する。フィードリーダーで実際にサムネイルが表示されるかどうかは各リーダーの仕様による。
- **<https://veripsa.com/image-review/>** に全公開記事の「サイト掲載画像」と「SNSカード画像」を並べた検品一覧を静的生成。公開済み記事のみ掲載し、`noindex` と `X-Robots-Tag` で検索登録対象から外す（完全な非公開ページではない）。ここで、余白や文字の読みづらさ、意味のズレを人が継続確認できる。
- 既存の毎日の自動記事発行とAPI無料枠は維持し、生成AI画像サービス・外部有料API・新しいDB・有料フォントは導入しない。

## Xで紹介する記事を選ぶ：無料の投稿デスク

- **https://veripsa.com/share-desk/** は公開済みの新着記事から、実際の掲載日を優先して、なるべく異なるジャンルの紹介候補を最大3本選ぶ。これは「面白さ」や「人気」のAI判定・ランキングではなく、投稿前に必ず人が内容を選ぶための候補一覧。
- 各候補に、Xでの投稿文（※創作と明記）、実際の記事へのリンク、Xで下書きを開くボタン、現在のOGP用画像（記事別PNGまたは承認済みJPEG）の保存用リンクをまとめる。画像の自動アップロードはできないため、必要なら画像を手動添付する。
- **Xへの自動投稿はしない。** 新規のSNSアカウント連携・ボット・X API・有料ツールを使用しない。人が実際に内容を確認し、1日2〜3本程度から手動で試す。全記事を機械的にXへ投稿してスパム化させない。
- 投稿文は原文の内容から生成し、未確認の反応数・PV・投票・架空の人気を記載しない。X由来の流入を既存の集計で区分できるよう、`utm_source=x&utm_medium=social&utm_campaign=share_desk` を付けるが、追跡URLや検索語はDBに保存しない。
- 紹介候補は次のビルドで自動更新される。更新がなくても「今日の速報」と偽装せず、実際の発行日を出す。投稿デスクは**ログイン不要の公開ページだがnoindex**で、サイトマップにも掲載しない。個人の非公開情報を置かない。
- RSS、記事自動投稿、コメント、投票、SEOには影響させない。Python標準ライブラリ・既存の無料Cloudflare配信だけで構成。

## 収益化準備（追加費用なし）

- `/advertise/` を広告・協賛の説明ページとして公開する。サイトのフッターと編集方針からたどれる。
- 現在はスポンサー・広告の掲載や契約を行わない。出稿検討者は公開GitHub Issueフォームから公開可能な概要だけを提出できる。フォームの内容・返信は誰でも閲覧できるため、個人情報・機密情報・見積書・非公開条件を収集しない。
- 広告・PRを開始する場合は契約や掲載内容を人間が確認し、読者に一目で分かる広告表示を必須とする。創作記事の内容を出稿者の都合で変更しない。記事の広告まみれ化を避ける。
- AdSenseアカウント・サイトの承認状況はGitHubのコードやads.txtの存在だけでは判定できない。AdSenseの管理画面で利用状況を確認し、サイト審査に通るまでは広告コードを配信しない。広告主・収益・閲覧規模・承認済みの状態を捏造しない。
- 広告の候補枠は記事末尾やフッターなど邪魔にならない場所から検討する。広告と記事の区別を明確にし、クリック誘導や自動リダイレクトなどは行わない。
- 収益化より先に、記事の独自性、Search Console上の検索登録と読者からの継続的な反応を改善する。記事数の自動増加だけをSEOの成功と見なさない。

## 読者の実測データで記事を見つける仕組み

- トップページの読者発見セクションは、最新20本までから、既存の `/api/engagement` GETで実測した閲覧ブラウザ数が5以上の候補を抽出。2本以上ある場合だけ上位3本を紹介する。少数時・API不調時は何も表示せず、架空のランキングや架空のPVを作らない。
- 計測開始以来の匿名ブラウザ数であり、実人数・PV・週間人気・再訪数ではない。高頻度発行によって記事の露出期間が違うため、順位差をコンテンツの質の因果関係と断定しない。
- 既存の閲覧API取得を再利用し、追加のAPIリクエストはしない。記事一覧は実際の本紙掲載データから埋め込み、DOMの `textContent` で安全に描画する。最大20本のため、記事総数が増えてもページの転送量は限定される。

## 記事間の回遊を実測する仕組み

- 読者が記事Aから別の記事Bへ移動した場合、既存の閲覧POSTにAの**slugだけ**を追加する。同じサイトの参照元である場合だけ記録し、URL・検索語・クエリ・IPは保存しない。
- Cloudflareの既存の`NewsroomStats`に、記事Aから別記事へ移動したことのあるブラウザ識別子を**一度だけ**記録する。記事Bへの遷移のたびに増やさない。DBの新しい種類や追加のAPIリクエスト・課金プランは不要。
- 公開APIの各記事に`continuedReaders`（元記事から別の記事へ進んだ匿名ブラウザの累計）を付ける。翌日の`analytics/daily/YYYY-MM-DD.json`にも`continued_readers`として保存する。
- これは**実人数・PV・クリック数・回遊率ではない**。ブラウザが参照元を伏せる場合は計上できない。数字が少ない間は有意な優劣を断定しない。
- 従来の訪問数・いいね・投票・コメントの集計と、X/検索の粗い流入分類は変更しない。収益化の検証材料としてのみ利用し、広告は自動で追加しない。

## 読者の反応

- src/worker.js の NewsroomStats は Cloudflare Workers Free の SQLite Durable Object を使用。new_sqlite_classes のマイグレーションで自動作成。
- ブラウザ内で生成したランダムIDのSHA-256を保存して、サイト初回来訪・記事初回閲覧・いいね・X共有ボタンクリックを集計する。IPや端末指紋はDBに保存しない。
- GET /api/engagement?articles=slug1,slug2 で人数・記事別リアクションのブラウザ単位の参考値を取得できる。
- 実人数・PV・実際のX投稿数ではない。API障害時は数字を表示せず静的本文は継続する。
- 無料の流入元推定：X・検索・その他外部・判別不能の4区分だけを計測。X共有URLの短いキャンペーン識別子・UTM種別・参照元ドメインをブラウザ内で分類し、カテゴリ名だけをAPIへ送信する。参照元URL全文・検索語句・IPアドレスは集計データベースに保存しない。
- 流入区分ごとの値は「その区分で訪れたブラウザ識別子の累計参考値」。複数経路で同じブラウザが重複し、合計は実人数・PVにならない。UTMは自己申告のため厳密な流入元証明ではない。導入前の過去データは復元できない。
- GitHub Actionsによる無料の日次スナップショット（analytics/daily/）に、APIが返した場合のみ集計済み区分別累計値を保存する。API未取得の場合、架空の0として記録しない。
- Freeプランの上限に達すると追加API処理が失敗する。勝手な有料プラン移行はしない。Workers契約がFreeであることはCloudflare管理画面で要確認。
### 読者コメント欄（追加課金なし）

- 各記事末尾にニックネーム制のコメント欄を表示。ログイン・メールアドレス不要。本文2〜180文字・ニックネーム16文字以内。
- Cloudflare Workers Free の **SQLite Durable Object `ReaderComments`** にコメントを保存。既存のいいね・閲覧統計用 `NewsroomStats` には一切手を加えない。D1/R2/有料API/外部広告は使わない。
- 1ブラウザにつき5分間隔・最大3件/日、サイト全体で最大20件/時・100件/日。記事ごとに最大100件保持し、新しい順に20件表示。個人情報の入力やURL投稿は禁止。
- 表示は `textContent` を使用してHTMLを解釈しない。自分の投稿は同じブラウザから削除可能。3件の異なるブラウザIDによる通報で自動的に非表示。ブラウザIDはSHA-256ハッシュで保存し、生のIPアドレスはDBに保存しない。
- **重要:** ブラウザID制限は本格的なBOT認証ではなく、IDを再生成すれば回避されうる。管理者は不適切な投稿を確認して削除すること。今後必要になれば無料のCloudflare Turnstile（サイトキーとシークレットの設定が必要）を追加する。
- 管理画面: `https://veripsa.com/assets/comments-admin.html`。コメントの確認・非表示・再表示・完全削除が可能。
- **管理用キーは任意だが設定推奨:** Cloudflare Dashboard → Workers & Pages → `mihassei-news` → Settings → Variables and Secrets に `COMMENTS_ADMIN_TOKEN` を **Secret** として追加する（ランダム24文字以上）。GitHubや公開JavaScriptに絶対に書かない。設定前は管理用APIだけ無効、一般読者のコメント投稿・通報は利用できる。
- コメントは動的APIによるため静的記事本文のSEO・RSS・サイトマップを変更しない。無料枠を超えた場合はAPIがエラーを返して停止し、追加請求のために有料プランへ変更しない。
- 各記事・記事カードの「コメント」から該当記事のコメント欄に移動可能。コメント数は偽装せず、実際の公開コメントだけを表示する。
- トップページの「みんなの未来予想」は直近20本の対象記事に実際のコメントがある場合に限り、その記事タイトルとコメント件数を最大3本表示。未承認/未検証のコメント本文をトップへ転記しない。
- `GET /api/comments/summary?articles=slug1,slug2` で公開状態のコメント件数を最大20件まとめて読み込み。ブラウザ内に最長90秒間だけ件数をキャッシュしてWorkersの消費を抑える。認証情報やコメント本文はサマリーに含めない。
- 投稿本文・ニックネームから明らかな携帯電話番号やURLを検出した場合に拒否する（完全な個人情報検出ではない）。



### 未来の判定 — 読者参加型の2択投票

- 各記事末尾に「この未来、本当にありそう？」の2択（「ありそう」「それはない！」）を設置。ログイン不要。
- **追加の有料機能はなし。** 既存の `NewsroomStats` SQLite Durable Object と `/api/engagement` に `vote` を追加。新しいDBや外部APIは不要。
- 既存のブラウザ識別子をSHA-256ハッシュ化し、1ブラウザ・1記事につき1票。繰り返し送信・違う選択肢への再送信では票は増えず、最初の選択を確定する（変更不可）。
- 選択肢ごとの公開済み投票数を既存の閲覧・いいね集計GETにまとめて返す。読者が投票するまで割合は非表示、投票後に**実際の合計**だけから割合を計算する。投票ゼロでは偽の数字を表示しない。
- 投稿失敗・無料枠超過時は投票済みと偽装しない。ブラウザIDはリセット可能で実人数・民意の集計ではない。運営が自動投票を作ることはしない。
- Node標準テスト（SQLite）で、初回投票、重複投票、選択変更防止、2択集計、既存の閲覧・いいね・共有・流入経路への影響を確認。

## 自動投稿と無料運用

**追加の従量課金を発生させない運用方針。** 本リポジトリの外部AI生成API接続コードとGeminiを呼び出すGitHub Actionsの定期発行ワークフローは削除済みです。APIキー、課金アカウント、外部有料モデルを登録する必要はありません。

- 記事生成・更新：ChatGPTの「未発生新聞 ジャンル別多頻度発行」定期タスク（日本時間7:30〜23:30の2時間ごと・9枠に設定済み）。契約中のChatGPTプランに含まれる機能の範囲で稼働し、外部の従量課金AI APIは呼ばない。
- 元ネタ収集：ChatGPTの標準検索を利用。X・掲示板投稿の無断スクレイピング・本文や画像の転載はしない。確認できるURLと投稿日時がある話題だけ採用。
- 更新先：接続済みGitHubの公開リポジトリ `RollNuts/mihassei-news`、`content/articles.json`。ジャンル別の1日9枠で各枠1〜2本の発行を目標とする（記事の公開は出典の確認、接続サービスの稼働、無料利用枠に依存し保証されない）。公開前にJSON妥当性、重複、安全性、フィクション表示、元記事の著作権への配慮を確認。
- GitHub Actions：`.github/workflows/check.yml` のテストのみ。**生成AIへのリクエストは行わない。** GitHub Freeの公開リポジトリの標準ホストランナーを使用。
- 自動サイト更新：Cloudflare WorkersのGit連携でmainの更新を検知し自動デプロイする。
- 画像：`scripts/build.py` が記事ごとに独立したSVGイラストを生成する。画像AIのAPI費用なし。
- 課金防止：Cloudflare Workers Freeを維持し、無料枠超過時は処理を停止する。R2・D1・有料の外部APIを使わない。外部APIの有料プランに接続しない。制限に達したら投稿を見送る（勝手に有料プランへ移行しない）。
- **既存コストは別**：`veripsa.com`のドメイン更新費と利用中のChatGPTプラン料金はゼロにはならない。新たな月額・従量課金を増やさない方針。
- CloudflareのGit連携と独自ドメインは設定済み。デプロイ失敗時はCloudflareのログを確認する。
- 自動発行は、ChatGPTの定期タスク実行時に必要なWeb検索・GitHub連携が利用できる場合のみ成功する。失敗しても成功を偽装しない。定期タスクの利用枠・サービス条件が変わったときは投稿を止める。

### 他のAIを使いたくなったら

文章の候補づくりや査読を別のAIサービスで試すことは可能。ただし複数AIへのAPI接続はしない。手動で候補を持ち込んでGitHubへ追記するか、追加課金のない公式連携が実際に利用可能なときだけ運用を拡張する。


生成した `dist/` を静的サーバーで公開する。

## 著作権と創作

元記事・X・5ch・Redditの文章や画像は転載しない。著作物の一部が偶然一致する可能性もあるので、独立した記事だけを公開する。元ソースへ明示リンクをつける。実際の人物を創作された犯罪・不正等に結び付けない。公式サービスと紛らわしいロゴを使用しない。本文・画像・RSSはフィクションと表示する。

## データ形式

`content/articles.json` に記事を追加する。各記事で `source.published_at` と `fiction_at` は日本時間のISO 8601（例 `2026-11-02T11:00:00+09:00`, `2031-11-02T11:00:00+09:00`）。2月29日は5年後に同日が存在しないので、例外的に自動生成をスキップする。

## ライセンス

記事本文・オリジナル画像の無断転載を許諾するものではありません。外部の素材・写真は同梱しません。

## 検索エンジン登録・広告審査

- Google Search Console: https://search.google.com/search-console/ で Domain property `veripsa.com` を追加し、Cloudflare DNS に Search Console が提示した TXT 値を登録。所有権確認後、`https://veripsa.com/sitemap.xml` を登録。
- 記事の `fiction_at` は読者向けに演出する創作日時。構造化データに記録する `datePublished` は、現実に本紙へ公開した `published_at`（JST ISO 8601）または古い記事の `published_on` であり、架空の未来日付を使わない。
- AdSense 審査用に `ads.txt` と `google-adsense-account` メタタグを登録済み。サイト所有権の確認後に、Google AdSense 側から審査申請する。承認される前に広告表示コードを実行しない。
- AdSense の承認と広告収益は保証されない。著作権・プライバシー・オリジナル性・広告ポリシーを確認し、承認されても読書を妨げる広告大量掲載はしない。
- `/privacy/` を公開し、匿名のブラウザ単位のアクセス測定と、写真表示時の外部通信などを明示している。

## 記事画像の品質管理（2026-11-02改訂）

**記事の毎日発行は止めない。** 画像の失敗だけで発行を止めず、外部サービスにも課金しない。

- 標準画像は `scripts/editorial_covers.py` が生成する **記事見出し入りのオリジナル新聞風SVG表紙（1200×675）**。実際の見出しと題材（電話、天気、野球、土産、情報セキュリティ、工場ロボットなど）に対応するシンプルな線画を使い、共通の色・余白・レイアウトで統一する。AI画像生成APIもネットワークも使わない。
- 検証した写真のみ任意で掲載可能。 `content/approved_photos.json` に **記事slug・正確なUnsplash作品URL・編集理由** を明示し、記事の `photo.source` が一致すること、作者・alt・ライセンスが揃うこと、ローカルJPEGが正常で充分な解像度・縦横比であることを確かめる。
- 記事JSONに `photo` があっても**自動採用しない**。承認されていない写真、未取得、縦長すぎる、不正なJPEGは自動でオリジナル表紙へ切り替える。過去にキャッシュ済みの画像も例外としない。実際の写真として偽装することもない。
- SNSのリンクカードには JPEG/PNG のみ使う。記事写真が非承認なら、`scripts/social_cards.py` が生成する記事別・自前の1200×630 PNGに切り替える。SVGを直接OGPへ指定しない。
- `scripts/cache_photos.py` も同じ審査リストを使い、未承認写真はそもそもダウンロードしない。無料のGitHub Actions + Python標準ライブラリのみ利用。
- 審査リストは **機械による意味理解やAI画像鑑定ではない**。表示形式・画像解像度・資料の整合性を自動検査し、内容との適合性は写真の承認時に人が確認する仕組み。今後写真を採用するには編集レビューが必要。
- 画像を変える際は著作権・クレジットも更新し、公開した記事の `modified_at` は内容が実際に変更されたときだけ更新する。画像の再ビルドだけで公開日時を詐称しない。
